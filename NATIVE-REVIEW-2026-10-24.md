## Main findings

| Claim | Verdict | Current evidence / qualification |

| 1. Duplicate IDs can trap Home/History | Still present; defensive correctness gap | `ios/Packages/TwilDiaryCore/Sources/TwilDiaryCore/HomeOverview.swift:33` and `HistoryQuery.swift:29,50,51` use `Dictionary(uniqueKeysWithValues:)` with workspace rows. `DiaryAPI.swift:153–164` appends page items without identity normalization. However, the supplied explanation about offset pagination is incorrect for this backend: `src/lib/server/workspace.ts:56,117,148,172` uses ID keyset pagination (`id > after`, ascending), and database IDs are primary keys. Normal concurrent writes do not establish the alleged overlapping-page scenario. Malformed/duplicate snapshots should still be rejected or normalized before publication, with safe projection fallbacks. Deduplicate events as well to avoid double-counting, not only dictionary construction. |
| 2. Saved-title season reveal race | Still present | `TitleDetailView.swift:332–344` has one global `revealing` flag. A replacement season task can return early while the old response is subsequently discarded. No current test covers this saved-title race. Existing CatalogEpisodeController cancellation tests cover a different implementation. Use a selected-season/request generation and cancellation/coalescing, not a single global gate. |
| 3. Stale notes/rating expectedVersion | Still present, with nuance | Notes Save uses `notesVersion` at line 60; it advances on title-version change only when the draft equals server notes (118–121). Edited drafts do not advance after an unrelated favorite/status write. The brief overstates ordinary watch behavior: `src/lib/server/watch-status.ts:33–35` bumps title.version only when the derived status changes, not for every episode tap; title PATCH and bulk status edits do advance it. Rating Save uses its opening/success version at 366–372. A conflict refresh can leave those captured versions stale, so retries can repeat 409; failed rating saves also reset the displayed draft to the server value. **Do not blindly retry with the newest version:** that could overwrite a genuine external edit. Preserve the draft and compare the edited field with its base; only rebase an unrelated-field version change, otherwise show a real conflict. |
| 4. Ratings absorb authentication errors | Still present; timeout fix does not solve auth classification | `CommunityRatingsController.swift:48–53` treats every non-cancellation error as unavailable. `DiaryStore.loadPublicRatings:262–277` does not route APIError.signIn through the session handler. Thus an expired Access response can be hidden as a score outage. Build 25 fixes long loading using small batches, deadlines and Retry, but auth and transport/provider error classification still needs work. `unrated` is already distinct from `unavailable`. |
| 5. Access login dead-end/retry | Still present | `AccessSignIn.swift:21–34` only reads cookies after exact `/api/session` completion, silently returns when the cookie is absent, and has no didFail/didFailProvisionalNavigation, bounded completion wait or retry state. Inspect valid cookies on trusted backend finishes/cookie changes while preserving strict secure-domain checks and server validation. Allow time for user-driven 2FA; do not impose a short login timeout. |
| 6. Every card refetches on every event | Addressed in build 25 source; full new regression acceptance pending | `Components.swift:335` now keys the task to `store.cardRevision(title.id)`. `DiaryStore.swift:183–212,278–305` indexes per-title inputs, invalidates only affected revisions, coalesces reads, retains bounded display cache and freshly validates writes. Pending mutation state is card/action scoped. New coalescing, unrelated-edit, cancellation and slow-category regressions are included in 25. The old `.task(id: store.workspace.events)` claim is stale. |
| 7. Home computes full history for four rows | Still present | `HomeView.swift:14–16` creates HomeOverview and all HistoryQuery entries inside body before prefix(4); `StatsView.swift:19` likewise builds its overview in body. History dates are already parsed once per event before sorting; the old repeated parse-inside-History-comparator allegation does not apply to current HistoryQuery. A recent/top-k projection should preserve exact source ordering and rewatch evidence; limiting unsorted events first is incorrect. |
